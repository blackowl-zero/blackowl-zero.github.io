UltraTech

TryHackMe · Linux · command injection → bcrypt crack → docker privesc

TryHackMe

Grey box

intro

UltraTech is a Linux box on TryHackMe. It is a grey-box assessment, so the only things you get are the company name and the server IP. The goal is to enumerate the services, land a shell, and escalate to root.

reconnaissance

First I ran an nmap scan on the target to see the open ports, the service versions, and a guess of the OS.

sudo nmap -sV -O <target>

The scan showed a handful of ports:

  • 21 · FTP
  • 22 · SSH
  • 8081 · Node.js
  • 31331 · Apache
Which software is using port 8081?
Node.js
Which software is using port 31331?
Apache

From the nmap output the distro was Ubuntu. Port 8081 was the first thing that looked interesting, and it was not a normal website. It was a small Node.js API exposing two endpoints, not two web apps like I first assumed.

vulnerability scanning

I started with the Apache server on 31331, because web servers usually give you more to work with. I checked robots.txt and it pointed me to utech_sitemap.txt. The sitemap listed some extra paths, one of them a /partners.html login page.

Looking at the site's JavaScript, I saw it was talking to the API on 8081. The API had two endpoints:

  • /auth · login
  • /ping · takes an ip parameter and pings it

The /ping one looked bad. Sending:

http://<target>:8081/ping?ip=8.8.8.8

gave back the raw output of the ping command. That means the input was going straight into a shell, classic command injection.

exploitation

I tried to chain a second command after the IP:

http://<target>:8081/ping?ip=127.0.0.1;ls

It worked. The response had the ls output right next to the ping output, so I had command execution as the user running the API.

Finding the database

I kept enumerating through the same parameter and found a SQLite database in the app folder.

http://<target>:8081/ping?ip=127.0.0.1;ls -la
...
utech.db.sqlite

I read it and pulled out two bcrypt hashes, one for admin and one for r00t.

Cracking the hash

I saved the r00t hash to a file and cracked it with john and the rockyou wordlist.

john --wordlist=/usr/share/wordlists/rockyou.txt hash.txt

The r00t hash cracked almost instantly to n100906.

SSH access

SSH was open on 22, so I reused the cracked creds.

ssh r00t@<target>

And I was in as r00t.

post-exploitation & privesc

After landing the shell I checked my user and groups.

id

r00t was in the docker group. That is an easy road to root, because docker runs as root and you can mount the whole host filesystem into a container.

docker images
docker run -v /:/mnt --rm -it <image> chroot /mnt sh

That dropped me into a root shell on the host with full access to the filesystem, so I could grab the flags and finish the room.

mitigation

  • The /ping endpoint should never put user input into a shell command. Validate the ip parameter properly and use a safe library instead of building the command as a string.
  • The utech.db.sqlite file should not sit in the app folder where it can be reached. Keep it out of the web root and fix the permissions.
  • bcrypt was a fine choice for hashing, but n100906 is a very weak password and cracked instantly, so enforce a stronger password policy.
  • Normal users should not be in the docker group unless they truly need it, because it is effectively root.
  • Internal APIs should not be exposed on a public interface, and everything should stay patched.
